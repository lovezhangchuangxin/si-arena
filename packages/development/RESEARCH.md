## 研究目标与预算

在预算内改进策略：对抗游戏争取战胜更多不同对手，单人游戏争取在不同种子下取得更高且稳定的得分；两者都与历史最佳版本比较。跑通代码、击败官方 bot 或达到某个胜率后，仍应继续有价值的实验；不承诺战胜所有对手或找到最优策略。

- 优先遵守用户指定的时间、场数或费用上限。未指定时，环境准备完成后默认研究 30 分钟，开始时说明预算和计划，无需等待确认。预留最后约 20% 时间做独立验证和交付。不要为凑时长空转；工具不可用、用户要求停止或无法继续验证时，保存成果并说明未完成的工作。
- 阅读游戏规则、SDK.md、release.json 和官方源码，必要时查看包内规则实现。SDK 说明接口，release.json 的 game 记录本地发行、配置和资源限制，官方 bot 供参考和对战。资料有矛盾时，用规则实现和小型对局核对并报告。
- 先验证容易误解的规则：同时行动如何冲突、倒计时何时归零、未调用动作时做什么、执行失败后如何恢复。记录预测、实际发生的 tick 和结论，不能只凭阅读声称已经验证。
- 至少提出三种不同的策略思路，说明适用局面、预期效果、可能的弱点和验证方法。优先测试最有价值的思路；反复微调同一个常数不算不同思路，也不要为凑数量省略验证。

## 迭代与历史最佳

1. 先测试已有策略。已有 bot.js 时，保存副本再运行，后续从表现最好的版本继续改进。
2. 在 research/ 保存带版本号的候选代码、历史最佳和实验记录。每组记录代码与对手版本、策略思路、完整命令、种子、适用时的人数与席位、结果、执行错误和回放路径。测试前保存源码，不直接覆盖最佳版本。
3. 每轮按“提出假设 → 修改 → 对照比赛 → 分析失败回放 → 保留或淘汰”推进。挑选有代表性的败局，找到关键 tick；必要时用日志或专门编写的对手确认原因。
4. 对抗游戏：对战官方示例、自己的历史最佳，以及预算内能编写的不同风格策略。保留能克制当前最佳的旧版本，避免把互相克制误当成全面进步。单人游戏：把官方示例、历史最佳和候选分别作为 --bot 运行，用同组种子比较成绩，不传 --opponent。所有策略都通过 arena 的正常沙箱和资源限制运行。
5. 用相同种子比较新旧版本；对抗游戏还固定对手、人数与席位，并让新版本直接挑战历史最佳；单人游戏比较逐种子分差、平均分和低分局。每次优先测试一个主要改动，同时检查执行错误和关键 tick 的 CPU 用量。结果支持改进且未引入执行错误时，才替换最佳；结果矛盾或样本不足时保留原最佳，记录原因。不要挑选有利种子或只报告对官方的最好成绩。

## 独立验证与交付

- 实验前划分两组不重叠的种子：一组调参，一组留到最后验证。种子 42 只是调试起点。若看过验证结果后继续据此修改策略，这组种子就不能再用于独立验证，必须另选新种子；预算不足时如实说明。
- 报告实际场数和执行错误。对抗游戏尽量覆盖多种对手，比较胜平负、冠军率与平均名次；多人游戏还比较不同阵容和人数。交换席位时交换 --bot 与 --opponent 的文件顺序，按玩家 ID 对应回实际文件。单人游戏报告平均分、最低/最高分和相对基线的逐种子表现；名次固定为 1，不能用 batch 胜率证明策略强度。
- 预算结束时，把验证表现最好的版本写入 bot.js，并重新测试最终文件。没有可靠进步就保留原最佳，不交付未经验证的最后一次修改。
- 在 research/ 保留后续可用的记录，简要报告最终策略、与官方和历史最佳的对照结果、新种子上的表现、执行错误、已知弱点和下一步思路。只上传 bot.js；平台仍只保存最新源码。
- 没有运行工具时，只能交付未经实测的代码，并明确说明未验证，不编造胜率、结果或回放。玩家要求“只输出代码”时遵从，也不要在注释中虚构测试结果。
