# 资源限额

本文定义平台资源默认值及每个游戏的覆盖规则。每个小游戏在自己的 manifest 中配置执行与日志预算；未指定的字段继承平台默认值。圈地游戏 `paper` 不覆盖这些字段，使用下表默认值。

`KiB = 1024 bytes`，`MiB = 1024 KiB`。所有 JSON 和文本大小按实际 UTF-8 字节数计算，不按 JS 字符串长度估算。

限制由平台发布的游戏配置提供，网站、下载包、上传 API 和执行器使用该游戏同一份完整配置。正式排位的客户端不能覆盖参数。当前 CLI 使用可信注册中的完整限额，没有供玩家覆盖预算的命令行选项。自定义可信本地注册若调整预算，工具必须展示差异，不能把结果作为线上行为保证。

## 游戏配置与继承

平台在 protocol 包中导出 `DEFAULT_RESOURCE_LIMITS` 与配置 schema。游戏 manifest 的 `limits` 只写需要覆盖的字段，省略与 `undefined` 表示继承；`null`、未知字段、非有限数、非正整数或单位错误均拒绝发布，不表示无限制。

```ts
export const manifest = {
  id: "another-game",
  limits: {
    cpuMs: 40,
    heapBytes: 64 * 1024 * 1024,
    memoryBytes: 128 * 1024,
    resultBytes: 192 * 1024,
    logs: { tickLines: 64 },
  },
};
```

上例覆盖 CPU、isolate 堆、Memory、执行结果容量和每 tick 日志条数，其余字段继承默认值。`logs` 按已知字段递归合并，不能用整个子对象替换导致默认日志大小限制丢失。同一场比赛的所有玩家使用相同的已解析限额。

发行时按“平台默认值 → 游戏字段覆盖”的顺序解析，写入发行清单的 `resolvedLimits`。网站和运行器读取冻结后的完整配置，不在每场比赛时重新套用当前平台默认值。默认值或游戏覆盖发生变化时发布新的游戏发行，已有发行与本地开发包不被静默修改。

发布检查同时验证预算关系：`wallMs >= cpuMs`，`stackBytes < heapBytes`，`memoryBytes < heapBytes`，`runnerMemoryBytes >= maxPlayers × max(heapBytes, 8MiB) + 128MiB`；单条日志不大于每 tick 日志预算，每 tick 日志预算不大于整场预算。结果和 IPC 预算必须容纳该游戏允许的动作、Memory、观察及封装编码。配置不一致时拒绝发布，不能在运行时悄悄降低游戏预算。

`errorBytes` 至少为 128 字节，以容纳错误类型和最小 JSON 封装；消息、名称和堆栈按最终编码后的大小截断，包含控制字符时也不能超过预算。

平台生成的观察、可信代码封装或控制消息超过发布预算属于系统错误，比赛失败且不计分；玩家动作、候选 Memory 或其执行输出超过预算，才按玩家当 tick 失败处理。错误与日志文本先截断至自身上限，不能因为诊断太长再次触发无界序列化。

运行服务在领取任务前检查本机是否能提供该发行要求的内存与进程资源；不满足时保留任务供具有足够容量的 worker 领取，不能降低限额运行后归咎于玩家。

## 玩家执行预算

| 项目                               | 平台默认上限 | 范围与处理                                                                                                                                            |
| ---------------------------------- | ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| JS 源码 `codeBytes`                | 256KiB       | 上传与本地加载时检查；超过则拒绝，原线上代码不变                                                                                                      |
| isolate 堆 `heapBytes`             | 32MiB        | 每玩家独立常驻 Isolate；包括源码、SDK、当前输入及跨 tick 全局/闭包缓存等全部存活对象与 ArrayBuffer；isolated-vm 的下限为 8MiB，更小的配置按 8MiB 建立 |
| 调用栈 `stackBytes`                | 256KiB       | 协议保留字段，不控制 V8 执行线程的栈大小；未捕获的栈溢出使当 tick 失败                                                                                |
| CPU 时间 `cpuMs`                   | 20ms         | 玩家代码求值阶段 isolate 线程的 CPU 时间；每 tick 重新计量，不结转、不累计 bucket                                                                     |
| 执行墙钟时间 `wallMs`              | 500ms        | 各 isolate 调用设置墙钟超时，超时销毁对应玩家环境；外层另监督整场进程无进展                                                                           |
| Memory `memoryBytes`               | 64KiB        | 每玩家每场；序列化后检查，不符合 JSON 协议或超限则丢弃当 tick 提交                                                                                    |
| 单个动作 `actionBytes`             | 1KiB         | 规范 JSON 动作；超过或不符合游戏 schema 时记为非法动作                                                                                                |
| 单个观察 `observationBytes`        | 128KiB       | 平台构造的每 tick 观察；超过属于系统错误，不归咎于玩家                                                                                                |
| 单个执行结果 `resultBytes`         | 96KiB        | 包含动作、新 Memory 与诊断，不包含独立流式日志                                                                                                        |
| 单条 IPC 消息 `ipcBytes`           | 1MiB         | 包括输入控制封装；发送方和接收方均检查                                                                                                                |
| 单条错误诊断 `errorBytes`          | 4KiB         | 名称、消息、堆栈和元信息的总和，超长截断                                                                                                              |
| 比赛进程总内存 `runnerMemoryBytes` | 512MiB       | 整场进程预算；启用 cgroup-v2 时由内核限制，包含玩家堆、Node、线程和宿主缓冲；local 模式不执行 RSS 硬限制                                              |
| 执行子进程初始化 `startupMs`       | 5s           | 启动 Node、加载 isolated-vm 并完成源码静态检查；首次初始化失败视为系统失败，不计分                                                                    |

CPU 在每 tick 进入玩家执行阶段时重新计量：首次和环境重建后的 tick 包含玩家源码编译/初始化，每 tick 都包含入口执行、游戏动作方法、日志格式化与命令/Memory 序列化。没有免费玩家初始化阶段。可信引导（运行时与上下文创建、观察与 Memory 注入、SDK 初始化和每 tick 公开视图构建）不计入 `cpuMs`，由 `wallMs` 兜底。平台固定开销不能算作玩家 CPU 超限；可信封装失败和整场进程无进展仍按系统失败处理。加载 isolated-vm、启动 Node 和等待操作系统调度同样不计入。资源上报中的 `cpuUsedUs` 与预算判定同源，只记录玩家自身消耗的 CPU；整 tick 线程 CPU 的阶段分解只保留在沙箱内部诊断中，不进入回放，避免平台固定开销被算作玩家超限。

执行进程每毫秒轮询 isolate 的 CPU 用量，超出即终止 isolate；正常返回后再次检查。超过当前游戏 `cpuMs` 的结果不能提交，默认值为 20ms；轮询存在粒度，资源预算不是微秒级抢占承诺。墙钟看门狗使用该游戏的 `wallMs`，用于阻断无法及时响应中断的路径，不用墙钟差值冒充 CPU。

### 进程硬限制的启用条件

isolate 堆预算不等于进程总内存预算。线上比赛要求每场独立资源组执行 `runnerMemoryBytes` 硬限制；当前生产 Compose 默认使用 `local`，尚未满足这一部署要求，不能据默认配置宣称已有每场 RSS 隔离。

| 执行模式    | 实际提供的限制                                                                 |
| ----------- | ------------------------------------------------------------------------------ |
| `local`     | isolate CPU、堆、墙钟及动作/Memory 等协议预算；没有整个进程的 RSS 硬上限       |
| `cgroup-v2` | 上述限制，加上 Linux 每场进程内存、swap 与线程数限制；需要已委托的 cgroup 目录 |

选择 `cgroup-v2` 后，建立资源组失败必须拒绝执行，不回退到 `local`。启用步骤和当前生产默认值见 [部署说明](deployment.md#进程资源隔离)。`stackBytes` 在两种模式下均为保留字段，不是已实施的字节级栈限制。

isolate 超限只使对应玩家失败；整个进程超限或退出属于整场系统失败，不归咎于某位玩家、不计分。

执行子进程和 Isolate 在本场成功 tick 间复用，任一执行失败后丢弃 Isolate/Context，下一 tick 以已提交 Memory 重建；跨 tick 堆缓存不是持久状态。缓存占满堆导致后续输入无法分配时记为该玩家 HEAP_LIMIT 并重建，不把缓存预算转嫁给平台。比赛进程被终止、OOM 或无进展时整场系统失败、不计分，不重建进程续跑。其他比赛进程继续执行。

## 日志预算

仅本地收集 `console.log/info/warn/error/debug`。服务端同名接口为空实现，不格式化、不保存玩家输出。

| 项目                                    | 平台默认上限 |
| --------------------------------------- | ------------ |
| 单条日志 `logs.lineBytes`               | 2KiB         |
| 每玩家每 tick 日志条数 `logs.tickLines` | 32 条        |
| 每玩家每 tick 日志总量 `logs.tickBytes` | 8KiB         |
| 每场所有玩家日志总量 `logs.matchBytes`  | 1MiB         |

日志内容在打印时转换为有界文本快照；先达到的条数或字节限制生效，之后不再格式化被忽略的输出。截断通过该 tick 的 `logsTruncated` 元信息展示，截断提示不挤占日志条数。

日志达到游戏发布上限只会截断，不直接判定执行失败。格式化日志所用 CPU 仍计入该游戏 CPU 预算，若因此超时则按普通 CPU 超限处理。比赛协调器已捕获的日志在玩家当 tick 失败后仍保留；比赛进程崩溃时不承诺保留未完成比赛的诊断。

## 执行并发与排队

以下是平台调度策略，不属于游戏可覆盖的玩家资源预算。worker 每次领取时重新读取当前可用内存，扣除本 worker 运行中比赛已预留的完整预算，通过数据库条件只领取冻结 runnerMemoryBytes 可满足的任务；领取后预留完整预算，任务结束释放。容量不足时继续轮询，内存恢复后即可接单，无需重启。该预留属于本 worker，部署多个 worker 时仍需在部署层分配总容量。

- 每个比赛 worker 默认同时执行 2 场比赛，共最多 2 个比赛执行进程；本地批量按 CPU、人数与可用内存选择并发。
- 同一比赛所有玩家的 isolate 独立分派，所有动作在统一结算前收齐或超时。
- 本地批量默认按 CPU、参赛人数与可用内存并发，`--jobs 1` 串行；按原种子顺序输出，单场系统失败不取消其他场次，批次汇总失败数并返回非零退出码。
- 用户在同一游戏同时只能有一个未完成的主动匹配请求；被动成为对手不受此限制。
- 任务等待不消耗玩家 CPU，不算执行超时；领取和执行不能自行创建新比赛。

## 配置管理与验收

每个游戏解析后的资源配置随发行固定，变更时发布新的游戏发行并同步更新网页和本地开发包。代码入口协议是否兼容由 botProtocolVersion 标识；资源变更不重置排位，现有源码仍需满足新发行的体积要求。实现必须验证默认继承、字段覆盖、日志子字段合并、发行配置冻结、普通策略可运行、超限隔离、诊断准确以及下一 tick 可重新调用。性能测试记录实际成本和吞吐量，不把这里的默认预算表述为已经测量的性能结果。

认证密码哈希、平台 API、规则引擎和渲染器不使用玩家 CPU 预算。它们属于各自服务的运行负载，不能伪装为玩家代码超限。
