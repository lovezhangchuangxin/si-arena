# SI Arena：炸弹人参赛提示词

这是 SI Arena 平台的炸弹人竞技：最多 4 个 bot 在同一张固定地图上放炸弹、炸墙、拾取道具，被火焰波及即出局，线上竞技场按最终名次结算炸弹人排位分（初始 1000）。目标是在预算内改进策略，并通过不同对手的对战检验效果。

最终交付可直接上传的 UTF-8 JavaScript 文件 `bot.js`，研究记录保存在本地。先读本文件的规则和结算顺序，再查 SDK.md 的接口与 release.json 的资源限制。安装、命令和更新方法见开发包 README.md。

## 对局与名次

- 2–4 人同场。固定 15 × 13 地图，坐标左上为 (0,0)，右为 x+1，下为 y+1，下标 `y * 15 + x`。x 与 y 都为奇数的格子是不可摧毁的石柱。
- 出生点是四个角，种子决定谁站在哪个角；每个角及沿两条边各延伸 2 格开局没有软墙。其余格子约 70% 是软墙，地图四向镜像，四角公平。每面软墙里可能藏着道具：约 20% 是 `fire`，20% 是 `bomb`，开局不可见。
- 每人初始同时最多 1 枚炸弹、火焰长度 2。每个 tick 所有存活玩家看到同一张完整地图，然后同时行动。最多 400 tick。
- **被火焰波及或被坍塌压住即出局**：不再收到观察，也不再执行代码。
- 存活人数不超过 1 时立即结束，存活者第 1 名。到 400 tick 时存活者按得分排名，相同并列。每炸开一面软墙 1 分，火焰击杀按覆盖死者的炸弹每枚 10 分（归属和例外见结算顺序）；出局者得分记 0。
- 出局者排在所有存活者之后，出局越晚名次越好；同一 tick 出局的并列。所有人同一 tick 出局时全部并列第 1。
- 线上排位按 Elo 逐对结算：普通参赛者之间按名次定胜/平/负，并列记平局；分数变化还取决于双方赛前排位，不能直接用名次推断涨分多少。官方 bot 不参与计分；本地比赛不改变线上排位。活下来比炸得多更重要。

## 核心循环：放弹、逃离、拾取

- `bomb()` 在脚下放一枚炸弹，本 tick 不移动；之后你可以离开，但任何人都不能再走进这一格。同时最多 `bombsMax` 枚，脚下已有炸弹时无效。
- 炸弹 `fuse` 放下时为 8，放下的那个 tick 结算就减到 7，之后每 tick 减 1，减到 0 爆炸。未被连锁提前引爆时，观察到 `fuse` 为 f 的炸弹在当前 tick 起第 f 次结算爆炸：f = 1 表示本 tick 结算就炸，你这一 tick 的移动必须离开它的火焰。
- 火焰从炸弹格向四个方向各延伸最多 `range` 格：遇到地图边缘、石柱或坍塌格停止（不含该格）；遇到软墙把该格炸开并停止；空地、道具、玩家、其他炸弹都穿过。火焰到达的其他炸弹同一 tick 连锁爆炸，连锁可以让一枚 `fuse` 为 7 的炸弹立刻爆炸——包括你刚放下的那枚。
- 火焰只存在于爆炸的那一个 tick。移动后站在火焰格上的人死亡，先于一切拾取判定。
- 炸开的软墙露出里面的道具；站上去即拾取：`fire` 火焰长度 +1（上限 8），`bomb` 同时炸弹数 +1（上限 6）。结算前已经在地上的道具会被火焰烧掉，本 tick 刚从软墙里露出的道具会保留。
- 从第 300 个 tick 的结算起，每 8 个 tick 由外向内坍塌一圈（第 0 圈是最外一圈，第 k 圈是到边缘最小距离等于 k 的格子），上面的软墙、炸弹、道具全部消失，站在上面的人死亡；第 5 圈在第 340 个 tick 坍塌后只剩中心 `(6,6)`、`(7,6)`、`(8,6)` 三格。`game.collapse.ticksToNextCollapse` 为 1 表示下一次结算就坍塌。

## 结算顺序

所有玩家根据行动前的同一个局面选择动作，再按顺序结算。移动看旧地图与旧炸弹，火焰看墙体摧毁前的地图，死亡与拾取看移动后的位置：

1. 移动：目标格在地图外、是石柱、软墙、坍塌格或有炸弹时留在原地。玩家之间不互相阻挡，可以同格、可以交换位置。
2. 放炸弹：按席位顺序，脚下没有炸弹且未达上限时放下 `fuse = 8`、`range` 等于当前火焰长度的炸弹。
3. 引信：所有炸弹 `fuse` 减 1，为 0 的爆炸，火焰按本 tick 开始时的地图计算，连锁反复处理到没有新爆炸；同一 tick 被炸开的软墙仍阻挡其他火焰。
4. 摧毁：火焰到达的软墙变空地并露出道具，火焰到达的地上道具消失；每面软墙给炸弹主人 1 分，多枚火焰同时到达归放置最早的那枚。
5. 火焰致死（`flame`）：移动后站在火焰格上的玩家死亡；每枚覆盖该格的炸弹分别给其尚未出局的主人 10 分，自己炸自己不得分。同一主人的多枚炸弹可重复计分，但 death.killerIds 按主人去重；本 tick 同时死亡者最终得分清零。此前已出局者留下的炸弹照常爆炸，不再为主人加分。
6. 拾取：存活玩家所在格的道具被拾取，多人同格都获得效果。
7. 坍塌（`collapse`）：坍塌 tick 时外圈消失，站在上面的玩家死亡。
8. 清理：本 tick 死亡的玩家移出地图，`tick` 加 1。

## 玩家接口

默认导出同步函数，每 tick（一次游戏更新）调用一次。调用方法选择动作，不通过返回值提交动作：

```js
export default function tick({ game, Memory }) {
  game.self.idle();
}
```

- `game.self.move("up" | "right" | "down" | "left")` 移动一格，`game.self.bomb()` 放炸弹，`game.self.idle()` 停留；方法均返回 undefined。
- 未调用动作方法时默认停留；同 tick 多次调用以最后一次为准。位置和地图本 tick 不变，所有动作收齐后统一结算。
- 入口只能返回 `undefined`。返回对象或 Promise 会产生 `ENTRYPOINT_ERROR`；方向等动作参数错误会产生 `INVALID_ACTION`。即使用 catch 捕获错误，本 tick 仍执行失败。
- game 及其内部数据只读。每 tick 使用当前传入的 game，不能调用旧 game 上的动作方法。

## game：可读取的数据

- `self`：自己的 `id`、`slot`、`position`、`bombsMax`、`fireRange`、`activeBombs`（场上自己的炸弹数）、`score`，以及三个动作方法。
- `opponents`：其他存活玩家，按 slot 排列，字段同 self 但没有动作方法。
- `eliminated`：已出局玩家的 `id`、`slot`、`tick`（出局时已完成的 tick 数）与 `causes`。
- `board.width`、`board.height` 为 15 与 13；`board.cells` 是长度 195 的数组：0 空地、1 石柱、2 软墙、3 坍塌格。软墙里的道具不可见。
- `bombs`：场上炸弹，按放置顺序，每项 `position`、`owner`（席位）、`fuse`、`range`。
- `powerups`：地上的道具，每项 `position` 与 `kind`。
- `collapse`：`startTick` 300、`interval` 8、`nextRing`（下一个坍塌的圈，全部坍塌后 `null`）、`ticksToNextCollapse`。
- `tick` 从 0 开始，表示已完成的结算次数；`maxTicks` 为 400。
- `events` 是上一 tick 结算产生的公开事件，首个 tick 为空：move、bomb-placed、explosion、pickup、collapse、death。explosion 的 `cells` 是上一 tick 的火焰格，death 的 `killerIds` 是击杀者。
- 不提供火焰预测、寻路、逃生或放弹时机 API；自行实现算法。完整字段和事件结构见 SDK.md。

## Memory 与资源

- 玩家接口 v1（发行与实际限额见 release.json）：源码和 SDK 在环境创建时加载一次，成功 tick 间复用 JavaScript 环境。全局变量、闭包、Map 与 TypedArray 可跨 tick 缓存，都计入堆内存用量。
- 任一 tick 执行失败后重建环境，全局变量、缓存和 API 模块状态清空，顶层代码重新运行；下一 tick 从上次成功的 JSON `Memory` 恢复。把恢复所需的计划与状态写进 Memory；每 tick 都以新传入的 game 为准。
- 资源预算读取 release.json 的 `game.resolvedLimits`，不要把其他游戏或旧发行的数值当作当前上限。首次及失败重建后的 tick 包含玩家模块初始化 CPU；`stackBytes` 是协议保留字段，不代表按该字节数限制 V8 线程栈。
- 抛错、超时、非法动作或超限时：该 tick 按 idle 处理，丢弃本次 Memory 修改，保留上次成功的内容，下一 tick 再次调用入口。停留不会自动避险：站在火焰格或即将坍塌的格子上，停留同样出局。

## 语言限制

不能使用 import、require、异步函数、Promise、网络、文件与 Node API；不要依赖 Date、现实时间或 Math.random。可用 console 输出调试日志，按限额记录，仅本地可见。

## 策略思路

以下思路需要实测。对手之后放置的炸弹会改变火焰，预测不能只看当前场上的炸弹。

- 把爆炸时刻、连锁、墙体变化与坍塌展开为随时间变化的危险格，寻找到达时安全、之后也有出口的路线；放弹前加入自己的炸弹重新规划。预测多 tick 时，同 tick 软墙仍挡火，后续 tick 才能穿过已经炸开的墙。
- 对手新放的炸弹可能改变连锁与封路，不能只按当前 fuse 倒计时行动；每 tick 重算并比较不同的安全余量。
- 通道入口的炸弹可能封住退路，但是否能逃还取决于出口、剩余引信、射程和未来炸墙。用专门编写的对手验证封路，避免把所有窄通道都当成必死区。
- 比较优先获取道具与直接施压的效果，检查获得火力是否抵得过绕路、引爆自己或延误进圈的风险。
- 坍塌前确认通往中心的路已开，按剩余结算次数安排炸墙与移动。最后只剩三格时，射程与放弹位置决定覆盖范围；若火焰覆盖全部可站格且爆炸前没有结束比赛，存活者会同 tick 出局。不要把任意一次中心放弹都视为必然同归于尽。

## 验证方法

- 满员对战命令：`pnpm arena run --bot ./bot.js --opponent ./bots/official.js --opponent ./bots/official.js --opponent ./bots/official.js --matches 20 --seed 42`。逐场读取 `match` 行的 `result.players`，按玩家 ID 统计冠军率和平均名次，并检查执行错误；批量胜负汇总不足以描述多人表现。用本地历史文件替换部分 --opponent，组成混合阵容。
- 只给 `--bot` 时自动加入 3 个官方对手，组成 4 人局；显式给出 `--opponent` 后人数为 1 + 对手数，最多 3 个对手。两人局和四人局都要测：地图尺寸与生成规则不随人数改变，但对手数量会影响炸墙速度、连锁与封路风险。
- 分析败局：events 里的 death 记录了出局原因和 `killerIds`，explosion 记录了每次爆炸的火焰格，据此定位是误判引信、被连锁、被堵在死胡同还是没有及时离开外圈。
- `pnpm arena dev --bot ./bot.js` 启动可视化调试页：在浏览器打开命令输出的网址，整场结束后逐 tick 查看各方行为。
